Building Time Circuits · Web

How the SwiftUI clock became a three.js page in one session

The pitch

Prompt Please create a web version of bttfclock, using three.js. You can create a repo called bttfclock-web. Please ask any clarifying questions — thanks.

The starting point was the iOS and macOS app: SwiftUI shapes for the segments, a 40-city catalog, three colour-coded rows, and a colon phase-locked to the wall clock. Its CLAUDE.md already described every constant, so the port could be faithful by construction rather than by eye.

Four questions first

Some decisions would change the whole shape of the project, so they came first:

  • How 3D? Subtle 3D: identical to the app head-on, with real depth (raised panels, recessed windows, bloom) and a gentle tilt towards the mouse or gyro. Not a free-orbit model. (The tilt was later removed; see Step 7.)
  • Tooling? No build step: ES modules, with three.js through an import map.
  • Scope? City settings panel, URL parameters mirroring the launch args, ported unit tests, and the full docs set.
  • Hosting? A public repo deployed to GitHub Pages.
Note Creating the repository from the session was refused (the GitHub integration couldn't create repos), so it was created by hand and then attached. A good reminder to check permissions before planning a push.

Step 1: port the pure layer, with tests

Everything that isn't pixels moved to js/models and js/services, with no DOM and no three.js, so Node's built-in test runner can exercise it directly:

  • segmentMaps.js: the 7- and 14-segment bitmask tables, including the A, S and V fixes the app made during its own development.
  • segmentGeometry.js: a line-for-line port of SegmentShapes.swift. It produces six-point beveled hexagons, with italic skew applied per point using the full character height.
  • layout.js: the SwiftUI HStack arithmetic, reproduced in "natural points". One test pins the row width to the Swift value, 358.52pt.
  • timeReadout.js: Intl.DateTimeFormat with hourCycle: 'h23', cached per zone. Unknown zones fall back to UTC, like the app's ?? .gmt.
  • cityStore.js: the same storage key, cap and semantics, with Storage injected so tests use an in-memory map.

All 35 Swift tests were ported, plus 18 more that cover DST, URL parsing, geometry and corrupt storage: 53 in total, run with node --test and no dependencies.

Step 2: the first render, and a washed-out glow

The scene uses the layout numbers directly as world units. The enclosure and panels are extruded rounded rectangles with procedural brushed-metal canvas textures. Each field gets a gel plane, an extruded bezel, a glass sheet and a canvas-drawn DYMO caption. All ghost segments in a row are merged into one ShapeGeometry.

Observation I'm seeing the whole clock drowned in coloured haze: the panels read light grey, the black windows look grey, and there's a red, green and amber fog around the chassis. Turning bloom off shows a crisp render that's almost identical to the app.

Two causes, two fixes:

  • The bloom spread. UnrealBloomPass blends five mips with weights [1, .8, .6, .4, .2], and even with radius: 0 the 1/16 and 1/32 mips smear light across the screen. Overriding them to [0.7, 0.4, 0.12, 0.02, 0] keeps the glow tight, like the app's stacked 2/5/11pt shadows.
  • Unequal LEDs. Red is dim in luminance terms, so a single multiplier made green and amber bloom far more than red. Each LED colour is now normalised to the same target luminance, so all three rows glow equally.

Step 3: one colour, two looks

The app draws pale litCore segments with saturated bloom-coloured shadows. In a single-pass bloom, a pale core would give a pale glow. The trick is to use the saturated lit colour at HDR intensity:

// Neutral tone mapping desaturates the hot core towards white (litCore),
// while the bloom keeps the full row colour (the bloom shadows).
lit: new THREE.MeshBasicMaterial({ color: hdr(color.lit, LED_LUMINANCE) })

Because the render target is half-float, colours above 1.0 survive to the bloom pass. Everything that isn't an LED stays under the 0.8 threshold, so bloom is selective without layers or a second render.

Step 4: draw only when something changes

A clock that changes twice a second doesn't need a 60 Hz loop. The final timing model:

  • One setTimeout lands on every wall-clock half-second, flips the colon, and recomputes readouts only when the minute changes.
  • requestRender() coalesces into a single rAF.
  • When a character changes, its mesh swaps to a cached (kind, mask) glyph geometry, with no allocation per tick.

The result is two frames per second at rest, which matters on a phone left on a desk as a clock.

Step 5: the CITIES panel

Settings is a native <dialog>, which gives focus trapping, Esc and the backdrop for free. Up and down buttons replace SwiftUI's drag handles so reordering works from the keyboard and with screen readers, and each row shows its LED colour and the city's local time. Search covers names and IANA zones, and adding is disabled at three cities.

The first version also tilted the panel towards the mouse, or with the phone's gyro. Step 7 explains why that went.

Step 6: testing visuals headless

As in the app's -frozendate workflow, the URL parameters make screenshots reproducible:

?frozendate=1985-10-26T01:21:00-07:00
?frozendate=2015-10-21T16:29:00-07:00&cities=hill_valley,london,tokyo

Playwright drove Chromium with SwiftShader (--use-angle=swiftshader). It served three.js locally by intercepting the CDN URL, and it checked add, remove, reorder, persistence across reload, the empty state and reset, with no console errors. One gotcha appeared along the way: URLSearchParams turns the + in +01:00 into a space, so the parser now restores it, and a test covers that.

Step 7: straight-on, and crisper LEDs

With the site live on GitHub Pages, the first real-device feedback came in:

Prompt It's running! Thanks! A couple of minor things — I don't think we need the tilt, just straight on is perfect. And the LED numbers are too blown out — too bright, and that makes them too fuzzy. I guess it's the bloom setting?

Removing the tilt was simple. tilt.js and ?notilt went away, and the render loop no longer needs to ease anything, so it renders exactly once per change.

The fuzziness was only partly the bloom setting. The root cause was the Step 3 trick itself. To let a brightness threshold separate the LEDs from the grey chrome text, the segments had to be driven far above 1.0. The tone mapper then bleached their cores, and the bloom spread that extra energy into a blur.

The fix was to stop over-driving the digits and draw the glow separately:

  • Digits are drawn at the app's exact litCore colour, with nothing above 1.0, so they stay crisp.
  • Each lit segment and lamp gets a glow twin: the same geometry, in the row's saturated bloom colour, on a layer only the glow render sees.
  • The twins are rendered into a small target, blurred by UnrealBloomPass, and added over the main image. The pass's internal renderTargetsHorizontal[0] holds the halo without the source, so the cores aren't doubled.

This mirrors how the SwiftUI app does it: a pale fill with coloured .shadow layers underneath. A side-by-side crop against the app's own screenshot now matches closely.
